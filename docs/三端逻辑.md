# init-tool、sys、RPA-agent

三套程序各管一段。init-tool 在客户机上发现盒子并建立管理员。sys 是给人登录的云控，负责任务和页面。RPA-agent 待在盒子旁边，一次做一步。盒子上的接口只有 init-tool 和 agent 会打，sys 不连盒子的局域网地址。

```text
局域网盒子 :8000 / 云机 RPA 端口
    ↑ 扫描、镜像、云机                 ↑ 执行技能、抓画面
init-tool（127.0.0.1:18789）          RPA-agent（一台盒子一个）
    │ 管理员、盒子、分配                  │ 注册、心跳、领取、状态、守护、画面
    └──────────► tk_mg ◄────────────────┘
                     ▲
                     │ 登录、盒子管理、行为中心、任务
                   sys（127.0.0.1:18080）
```

本机库的地址和密码见 `docs/数据库.md`。sys 用的库是容器 `tk-mg-postgres-1` 里的 `tk_mg`，本机端口 `127.0.0.1:5433`。

## 1. 各自做什么

| 程序 | 做什么 | 不做什么 |
| --- | --- | --- |
| init-tool | 打开即主页，无需登录。UDP 扫描盒子，读状态，管镜像和云机，注册管理员，把盒子分给管理员 | 不提供云控页面，不下发行为链 |
| sys | 登录、成员权限、账号、盒子展示、行为链、任务入库、agent 协议、画面中转 | 不扫描局域网，不打盒子 `:8000` 装镜像或读固件 |
| RPA-agent | 向 sys 注册和心跳，按坑位领一条步骤，打盒子执行，回报状态，有人看画面时推截图 | 不决定守护脚本，不保存行为链，不创建管理员 |

登录的人用 init-tool 建出来的管理员账号进入 sys。sys 只列出分给该管理员的盒子。这个管理员名下没有盒子时，盒子列表是空的。同一 `user_group` 里的成员和管理员看到同一批盒子、同一批行为链。

## 2. init-tool

监听 `127.0.0.1:18789`。默认库是 `postgres://hmg:hmg@127.0.0.1:5432/hmgdb`，由 `INIT_DATABASE_URL` 改。空库时从 `data/init-tool.json` 导入。

它自己的表：

| 表 | 内容 |
| --- | --- |
| `init_admin` | 管理员。用户名、邮箱、密码哈希、是否启用 |
| `init_admin_box` | 哪台盒子分给哪个管理员 |
| `init_box` | 扫到的盒子。IP、型号、在线、固件、磁盘、内存 |
| `init_session` | init-tool 自己的会话 |

主要接口：

| 接口 | 作用 |
| --- | --- |
| `POST /api/register` | 新建管理员 |
| `GET /api/admins` | 管理员列表 |
| `POST /api/admins/update` | 修改管理员 |
| `POST /api/admins/delete` | 删除管理员 |
| `POST /api/admins/disable` | 停用管理员 |
| `POST /api/scan` | 广播扫描 |
| `POST /api/probe` | 探测指定盒子 |
| `GET /api/boxes` | 盒子及当前分配 |
| `POST /api/boxes/refresh` | 刷新已有盒子的状态 |
| `POST /api/assign` | 把选中的盒子分给一个管理员，或取消分配 |
| `GET/POST /api/images`、`/api/box-images` | 镜像列表、拉取、上传、导出、删除 |

扫描向每个本机 IPv4 网卡广播 `lgcloud`，端口 `7678`，默认等 8 秒。回复格式是 `前缀:盒子ID[:型号]`，来源 IP 记成这台盒子的地址。

分配只改 `init_admin_box`。一台盒子同时只属于一个管理员：先删掉旧关系，再写入新的。管理员必须存在且启用。传入的管理员 ID 为 0 时只解除分配。

sys 认的是 `tk_mg` 里的数据，不是 `hmgdb`。云控侧的约定是：

- 管理员在 `app_user`，`role = administrator`，`provisioned_by = init-tool`。
- 盒子在 `device`，有 `external_id`，`assignee_user_id` 指向这个管理员，并且不在未分配分组 `00000000-0000-4000-8000-000000000001`。
- sys 的成员页面不能改、不能删 `provisioned_by = init-tool` 的账号。新建管理员只能在 init-tool 做。

当前 init-tool 源码写入的是 `hmgdb` 的 `init_*` 表，仓库里还没有把管理员和分配同步进 `tk_mg.app_user` / `device` 的代码。联调目标是由 init-tool 写入 sys 的库。在那一步接上之前，sys 只会显示 `tk_mg` 里已经带上上述标记的管理员和盒子。

## 3. sys

页面在 `127.0.0.1:18080`。人用 cookie `tk_mg_session` 登录，会话在 `app_session`，库存的是令牌哈希。agent 不用这个 cookie，它用 `Authorization: Bearer`，sys 拿令牌的 SHA-256 去对 `device_agent.token_hash`。

### 3.1 谁能看见什么

当前用户先找到自己所属的 init-tool 管理员：自己就是这个管理员，或者和这个管理员在同一个 `user_group`。盒子、行为链、标签都挂在这个管理员上。

`GET /api/devices` 的条件是：盒子启用、有 `external_id`、已离开未分配分组、分配给上述管理员。备注和分组来自 `box_remark`、`box_group`，也按这个管理员分开。成员给盒子打的标签，改的是 `device.remark_id` 和 `device.box_group_id`。

### 3.2 行为链

表是 `behavior_chain`。一条链按管理员共享，成员看到的是同一管理员名下的链。

| 列 | 含义 |
| --- | --- |
| `parameters` | 步骤数组，形状与任务参数相同：`[{"skill","input"}]` |
| `param_scopes` | 每个参数是内部还是外部。保存时外部参数写成空字符串 |
| `guards` | 每步的守护，与步骤平行，不写进 `parameters` |
| `delays` | 每步做完后的等待毫秒数，0 到 60000 |
| `origin` | `rpa` 或 `ai` |
| `last_tested_at` | 对已保存的链下发被接受的时间 |

接口是 `GET/POST /api/behavior-chains`、`DELETE /api/behavior-chains/:id`、`POST /api/behavior-chains/:id/tested`。技能清单 `GET /api/skills` 来自代码，不入库。页面上「必须先测试才能保存」只记在浏览器里，刷新就没了。

### 3.3 一次下发

`POST /api/tasks` 要带 `Idempotency-Key`。同一个分组里这个键已经有任务，就返回原来的任务。

写入：

1. `execution_task` 一行，状态 `queued`，`executor_key` 为 `box-agent`，`parameters` 是整段步骤。
2. 每个步骤一行 `execution_task_step`。`kind` 是技能名，`parameters` 是这一步的参数，`guards` 是这一步的守护，`after_ms` 是做完后的等待，`target` 里有坑位号。坑位能对上 `device_instance` 时写入 `instance_id`。
3. `pg_notify('agent_task', 盒子ID)`，叫醒正在长轮询的 agent。
4. `operation_log` 记一条「已下发」。

`GET /api/tasks/:taskId` 把任务状态和各步骤状态读回来，给行为中心的测试结果用。

创建、重启、删除云机这类技能不能和别的步骤拼在同一次下发里。延时或守护格式不对，接口拒绝，不入库。

### 3.4 画面

页面要看某个坑位时，`POST /api/devices/:deviceId/watch` 写 `device_watch`，15 秒过期。agent 心跳的回应里带着这些坑位。agent 把 JPEG `POST /agent/frames`。没有未过期的观看记录，或者图是空的、超过 2MB，sys 直接丢掉。画面放在进程内存，键是 `盒子ID#坑位`，保留约 15 秒。页面用 `GET /api/frames` 取最近一张。

### 3.5 成员

成员接口只允许管理员调用。人在 `app_user`，组和人的关系在 `user_group`，分组在 `access_group`。页面权限在 `user_page_permission`；这个人还没有个人记录时用 `role_page_permission`。管理员不查这两张表。改权限或停用会作废该成员的 `app_session`。操作记入 `audit_event`。

init-tool 创建的管理员不走这套修改和删除。

## 4. RPA-agent

一台盒子一个进程。环境变量：

| 变量 | 作用 | 默认 |
| --- | --- | --- |
| `BACKEND_URL` | sys 地址 | `http://127.0.0.1:18080` |
| `BOX_ID` | 盒子外部 ID，对应 `device.external_id` | `box-dev` |
| `AGENT_TOKEN` | 注册和之后所有 agent 请求的令牌 | 开发用 `dev-token` |
| `DEVICE_HOST` | 这台盒子的地址，用来打本机接口 | `127.0.0.1` |
| `AGENT_LOG_ADDR` | 本机日志页 | `127.0.0.1:18790` |

启动后先向 `POST /agent/register` 注册。sys 核对令牌和盒子 ID，写入 `device_agent`，并把 `device.status` 标成在线。注册成功后开两个循环：心跳，以及领取任务。

### 4.1 心跳

默认约 15 秒一次，`POST /agent/heartbeat`。内容是盒子的型号、固件、内存、磁盘，以及坑位列表。坑位来自盒子自己的接口，15 秒内不重复拉取。sys 更新 `device` 和 `device_instance`。

回应里有三样东西：要取消的任务、仍处于守护中的任务、当前有人在看的坑位。观看列表变化时，agent 马上再打一次心跳，好尽快开始或停止推画面。

### 4.2 领取

`POST /agent/tasks/claim?boxId=...&wait=25s`。没有待执行步骤时，sys 把这个请求挂起，最多约 25 秒；期间有人下发，`pg_notify` 会把它叫醒。仍然没有任务就返回 204，agent 立刻再领。

一次领取只返回当前序号最小的一条 `pending` 步骤，不是整条链。日志里的 `claimed 任务ID index=坑位 任务ID@1`：`index` 是坑位号，`@1` 是模板版本号，不是第 1 步。同一次任务的每一步都会打出同一行任务 ID 和坑位。

领取时 sys 占住 `execution_task_device_lease`，并记 `execution_task_run`。这个坑位在租约释放前，页面上显示忙碌。

不同坑位在 agent 里各有一条执行队列，所以两个坑位可以同时做。同一个坑位上的步骤按领到的顺序做。

### 4.3 执行一步

agent 按领取结果连接这个坑位的 RPA 端口和安卓接口，然后：

1. 回报 `running`。
2. 若这一步不是「守护结束后回来继续」，就调用这一步的技能。失败则整步失败，sys 把同任务里其余待执行步骤取消，任务改为 `failed`。
3. 技能成功后，按 `after_ms` 等待，最长 60 秒。等待发生在守护探测之前，让画面先稳定。
4. 这一步带守护，并且角色是原来的步骤时，进入守护。角色是插入的点击时，只执行点击，不再套守护。
5. 回报这一步的结果。后面还有 `pending` 步骤时，任务回到 `queued`，下一次领取再拿下一步。没有了，任务改为 `succeeded`。

agent 不在步骤之间另加固定停顿。看起来很快，是因为领取、执行、再领取是连着的。

### 4.4 守护

探测脚本在 sys 的 `guards.ts`，不在 agent 里。现在有两个，顺序固定，和页面上开关的点击顺序无关：

| 代码 | 名称 | 判定 | 探测 |
| --- | --- | --- | --- |
| `ad` | 广告通过 | 节点 XML 的 `text` 含 `Settings` | `DumpNodeXmlEx` |
| `transcode` | 转码通过 | 节点 XML 的 `text` 含 `Apps` | `DumpNodeXmlEx` |

只打开一个时，只检查那一个。两个都打开时，先广告，再转码。

对话是：

1. agent 先做完原技能和延时。
2. `POST /agent/tasks/:id/guard`，第一次不带 `output`。sys 返回 `{action:"probe", skill, input, label}`。
3. agent 执行这个技能，把 XML 放进 `output` 再提交。
4. XML 里没有标记：sys 把守护下标加一，返回通过。还有下一个守护就立刻再探测。
5. XML 里有标记：sys 把原步骤改成 `held`，任务改成 `ood`，在原步骤后面插入一条 `ClickNode`，只带文字和序号。租约先放开，agent 结束这一次领取。下一次领到的是这条点击。
6. 点击做完后，原步骤回到 `pending`，阶段为 `guard`，原技能不会再做一遍。agent 从下一个守护继续。全部通过后，原步骤记为成功。

点击文字节点时，agent 会避开「字在小标签上、实际点到上一行大按钮」的情况：只按文字匹配时，点拥有该文字、且不超过屏幕约 60% 的可点击祖先。这是为了点到 Apps 那一行，而不是上一行的 Connection。

`OOD 执行` 用的是 sys 带回的守护名称。`OOD 完成，继续原步骤` 只在点击做完、原步骤的守护全部通过时打印。

### 4.5 画面

心跳得知某个坑位有人看之后，agent 抓该坑位的画面并 `POST /agent/frames`。sys 先查 `device_watch` 还在不在有效期内。页面自己拉 `GET /api/frames`，agent 不把画面直接送给浏览器。

## 5. 一条任务怎么走完

以行为中心里一次两步的点击为例，第一步开了广告通过和转码通过，延时 1500 毫秒。

1. 页面 `POST /api/tasks`。sys 写入 1 条任务、2 条步骤，并通知这台盒子。
2. agent 领到第 1 步，在对应坑位上执行点击，然后等待 1500 毫秒。
3. agent 向 sys 要探测。sys 指定 `DumpNodeXmlEx`。agent 导出节点并送回。
4. 没有 `Settings`，广告通过。sys 要求再探测一次。没有 `Apps`，转码通过。第 1 步成功。
5. 若导出结果里有 `Settings`，第 1 步暂停。agent 先领到并执行点击 Settings，再回来继续检查 Apps。原点击不会重做。
6. agent 再领第 2 步，做完后任务成功。页面 `GET /api/tasks/:taskId` 看到每一步的状态。

行为链本身不被这次执行改写。执行记录在 `execution_task` 和 `execution_task_step`。链上只在「测试一条已保存的链并且下发被接受」时更新 `last_tested_at`。

## 6. 和旧接口的边界

sys 上还挂着按分组管理设备、以及按分组提交任务的接口。按分组提交任务写的也是 `execution_task`，并额外写 `execution_task_event`、`execution_task_outbox`。行为中心和盒子控制台现在走的是 `POST /api/tasks`。

`operation_task`、`operation_task_template`、`operation_task_run`、`operation_task_allocation`、`operation_task_claim` 是更早的任务表。这三端当前这条链路不读写它们。运营中心的任务列表页面仍使用浏览器里的本地数据。

接口和表的对照见 `docs/四块接口.md`。
