# 行为中心、成员与权限、盒子管理、任务下发

下面列出的是这四块当前会走到的接口，以及每条接口读写的表。登录态用 `app_session` 里的 `tk_mg_session`。盒子上的 agent 用 `device_agent.token_hash` 校验。

## 行为中心

| 接口 | 表 |
| --- | --- |
| `GET /api/skills` | 无。技能目录在代码里 |
| `GET /api/behavior-chains` | `behavior_chain` |
| `POST /api/behavior-chains` | `behavior_chain` |
| `DELETE /api/behavior-chains/:id` | `behavior_chain` |
| `POST /api/behavior-chains/:id/tested` | `behavior_chain` |
| `POST /api/tasks` | `execution_task`、`execution_task_step`、`device_instance`、`operation_log` |
| `GET /api/tasks/:taskId` | `execution_task`、`execution_task_step` |
| `GET /api/devices` | `device`、`box_remark`、`box_group`、`app_user`、`user_group` |
| `GET /api/devices/:deviceId/slots` | `device_instance`、`execution_task_device_lease` |
| `POST /api/devices/:deviceId/watch` | `device_watch` |
| `GET /api/frames` | `device_watch`。画面在内存，不入库 |
| `GET /api/operation-logs` | `operation_log` |

行为链和一次下发是两套数据。`behavior_chain.parameters` 的形状与 `execution_task.parameters` 相同，都是 `[{"skill","input"}]`。守护开关在 `behavior_chain.guards`，步骤延时在 `behavior_chain.delays`，这两项不写进 `parameters`。保存时内部参数原样留下，外部参数写成空字符串。

同一管理员名下的成员共用这些行为链：先找到当前用户所属管理员，再按 `administrator_id` 读写。测试一条已保存的链时，下发成功会更新 `last_tested_at`。页面上的「必须先测试再保存」只记在浏览器里，刷新就没了。

选盒子和坑位用上面的设备和坑位接口。真正执行走下面的任务下发。

## 成员与权限

| 接口 | 表 |
| --- | --- |
| `GET /api/members/pages` | 无。页面清单在代码里 |
| `GET /api/members/display-name` | `app_user` |
| `GET /api/members` | `app_user`、`user_group` |
| `POST /api/members` | `app_user`、`user_group`、`user_page_permission`、`audit_event` |
| `PATCH /api/members/:memberId` | `app_user`、`user_group`、`app_session`、`audit_event` |
| `DELETE /api/members/:memberId` | `app_user`、`user_group`、`app_session`、`audit_event` |
| `GET /api/members/:memberId/permissions` | `user_page_permission`，没有个人记录时读 `role_page_permission` |
| `PUT /api/members/:memberId/permissions` | `user_page_permission`、`app_session`、`audit_event` |
| `GET /api/members/groups` | `access_group`、`user_group` |
| `POST /api/members/groups` | `access_group`、`audit_event` |
| `GET /api/access/groups` | `access_group`、`user_group` |

这些成员接口只允许管理员调用。列表里能看到自己，以及和自己在同一个 `user_group` 里的成员；其他管理员不出现。

页面能不能看、能不能删，按人存在 `user_page_permission`。这个人还没有个人记录时，用角色表 `role_page_permission`。管理员不查这两张表，页面全部可看可删。改权限或停用成员时，会作废该成员的 `app_session`，对方需要重新登录。新建成员时写入该角色的默认页面权限，并挂到所选分组。

分组本身在 `access_group`。人和组的关系在 `user_group`。管理员和成员能互相看见同一批行为链、盒子，靠的就是这张关系表。

## 盒子管理

当前盒子页用的是下面这组，不走「按分组创建设备」那套接口。盒子由初始化工具写入 `device`，并填上 `external_id`、`assignee_user_id`。这里只展示已经分配、且分配给当前管理员的盒子。

| 接口 | 表 |
| --- | --- |
| `GET /api/devices` | `device`、`box_remark`、`box_group`、`app_user`、`user_group` |
| `GET /api/box-labels` | `box_remark`、`box_group` |
| `POST /api/box-remarks` | `box_remark` |
| `DELETE /api/box-remarks/:id` | `box_remark` |
| `POST /api/box-groups` | `box_group` |
| `DELETE /api/box-groups/:id` | `box_group` |
| `POST /api/devices/labels` | `device`、`box_remark`、`box_group` |
| `GET /api/devices/:deviceId/slots` | `device_instance`、`execution_task_device_lease` |
| `POST /api/devices/:deviceId/watch` | `device_watch` |
| `GET /api/frames` | `device_watch`。画面在内存 |
| `POST /agent/register` | `device_agent`、`device` |
| `POST /agent/heartbeat` | `device_agent`、`device`、`device_instance` |
| `POST /agent/frames` | `device_watch`。画面写入内存 |
| `POST /agent/events` | `operation_log` |

备注和盒子分组按管理员分开，存在 `box_remark`、`box_group`。给盒子打标签时，改的是 `device.remark_id` 和 `device.box_group_id`，只能改分配给这位管理员的盒子。

坑位在 `device_instance`，由 agent 心跳上报后更新。有未释放的 `execution_task_device_lease` 时，坑位显示忙碌。

看画面时，页面先写一条 15 秒的 `device_watch`。agent 心跳里会收到要推的坑位，再把画面 `POST /agent/frames`。没有人在看，画面直接丢掉。页面用 `GET /api/frames` 取最近一张。

服务上还挂着按分组管理设备的接口：`/api/groups/:groupId/devices` 及其状态、实例、命令。它们读写 `device`、`device_instance`、`device_command`、`device_command_event`。当前盒子页的列表、备注和分组不走这些接口。

## 任务下发

行为中心和盒子控制台的下发都进同一条链路。

| 接口 | 表 |
| --- | --- |
| `POST /api/tasks` | `execution_task`、`execution_task_step`、`device_instance`、`operation_log` |
| `GET /api/tasks/:taskId` | `execution_task`、`execution_task_step` |
| `POST /agent/tasks/claim` | `execution_task`、`execution_task_step`、`execution_task_device_lease`、`execution_task_run`、`device_agent` |
| `POST /agent/tasks/:id/status` | `execution_task`、`execution_task_step`、`execution_task_device_lease`、`execution_task_run`、`operation_log` |
| `POST /agent/tasks/:id/guard` | `execution_task`、`execution_task_step`、`execution_task_device_lease`、`execution_task_run`、`operation_log` |
| `POST /agent/heartbeat` | 领取等待期间，心跳里带回取消和守护中的步骤 |

页面提交时带上 `Idempotency-Key`。同一个分组里这个键已经有任务，就直接返回原来的任务，不会再插一行。任务头写入 `execution_task`，状态为 `queued`。每个步骤一行 `execution_task_step`，`kind` 是技能名，`parameters` 是这一步的参数，`guards` 是这一步要跑的守护，`after_ms` 是这一步做完后的等待。然后用 `pg_notify('agent_task')` 叫醒正在等待的 agent。

agent 一次 `claim` 只拿走序号最小的一条 `pending` 步骤，并占住坑位租约。做完用 `status` 回报。后面还有待执行步骤时，任务回到 `queued`，下一次领取再拿下一步。全部成功后任务改为 `succeeded`。某步失败则剩下的待执行步骤取消，任务改为 `failed`。

步骤带守护时，agent 先做原技能，再问 `guard`。第一次不带结果，服务按守护脚本返回要调用的探测技能。agent 只执行这个技能，把结果再送回来。脚本判断没有障碍就通过，继续下一个守护；发现障碍就把原步骤改成 `held`，在它后面插入一条点击步骤，任务状态改为 `ood`。agent 先执行这条插入步骤，再回到原步骤继续后面的守护。守护顺序固定为广告通过、转码通过。探测脚本在服务端，agent 不保存脚本。

另有一组按分组的任务接口，写的是同一批执行表，并额外写 `execution_task_event`、`execution_task_outbox`：

| 接口 | 表 |
| --- | --- |
| `POST /api/groups/:groupId/tasks` | `execution_task`、`execution_task_step`、`execution_task_event`、`execution_task_outbox` |
| `GET /api/groups/:groupId/tasks` | `execution_task` |
| `GET /api/groups/:groupId/tasks/:taskId` | `execution_task`、`execution_task_step` |
| `POST /api/groups/:groupId/tasks/:taskId/cancel` | `execution_task` |
| `POST /api/groups/:groupId/tasks/:taskId/reconcile` | `execution_task`、`execution_task_run` |

行为中心现在走的是上面的 `POST /api/tasks`。运营中心里的任务列表页面仍使用本地数据，没有调用这组接口。库里的 `operation_task`、`operation_task_template`、`operation_task_run`、`operation_task_allocation`、`operation_task_claim` 是更早的任务表，这四块当前接口不读写它们。
