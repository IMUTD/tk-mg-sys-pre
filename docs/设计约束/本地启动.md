# 本地启动与账号

当前仓库包含 **前端 `apps/web`、后端 `apps/api` 和独立 `apps/worker`**。任务经 PostgreSQL outbox 执行；尚无魔云腾真实供应商协议或投屏服务。

本文记录本仓库的登录账号，以及管理前端的启动方式。账号仅供本地开发，生产环境不要使用。

## 登录账号

本地首位管理员由 `infra/.env` 中的引导变量创建，当前为：

| 项目 | 值 |
|------|-----|
| 邮箱 | `admin@example.internal` |
| 密码 | `Admin123!Local` |
| 角色 | 管理员 |

没有内置运营员 / 销售员 / 工程师账号。登录管理员后，在侧栏 **成员与权限** 里新建成员（密码无长度和格式限制）。名字会从动漫、影视、动物和明星名里随机分配；名单展示账号（邮箱），密码只在创建或重置时用于写入哈希，不会在名单或 API 响应中返回。登录页仍填邮箱；登录后顶栏和个人设置显示成员名字，不显示邮箱。

每个角色创建时写入默认页面权限：部长默认可删本部门页和资源中心，普通成员默认不能删；资源中心全员可见；工作日志仅管理员可见；运营概览不能开删除。删除按钮和删除接口只认「可删除」，不能用「能看就能删」。创建后再从「成员权限」列微调最终权限。该页只有管理员能进。

首次部署或清空数据库后，需要执行一次引导，邮箱已存在时会拒绝覆盖：

```powershell
cd tk-mg-sys
docker compose --env-file infra/.env -f infra/docker-compose.yml --profile bootstrap run --rm bootstrap-admin
```

以本机 `infra/.env` 为准。模板 `infra/.env.example` 里的管理员密码是占位符 `CHANGE_ME_ADMIN_PASSWORD`，不能直接登录。

## 前端启动

包管理器用仓库锁定的 pnpm（`packageManager: pnpm@10.28.2`）。Windows 上若 `pnpm` 不在 PATH，用 `corepack pnpm`。

### 1. 安装依赖

在仓库根目录 `tk-mg-sys`：

```powershell
corepack enable
corepack pnpm install
```

### 2. 开发模式（日常改前端）

```powershell
corepack pnpm --filter @tk-mg/web dev
```

浏览器打开 [http://127.0.0.1:5173/login](http://127.0.0.1:5173/login)。登录成功后进入 `/overview`。

Vite 会把 `/api` 代理到本机 API，默认 `http://127.0.0.1:3000`。若 API 不在 3000 端口：

```powershell
$env:VITE_API_PROXY = "http://127.0.0.1:你的API端口"
corepack pnpm --filter @tk-mg/web dev
```

只起前端、不起 API 时，页面能打开，但登录会失败。

### 3. 生产构建预览

```powershell
corepack pnpm --filter @tk-mg/web build
corepack pnpm --filter @tk-mg/web exec vite preview --host 127.0.0.1 --port 4173
```

浏览器打开 [http://127.0.0.1:4173/login](http://127.0.0.1:4173/login)。预览是静态文件，默认不代理 `/api`。

### 4. Docker 整栈（含前端）

```powershell
docker compose --env-file infra/.env -f infra/docker-compose.yml up -d --build
```

入口由 `infra/.env` 的 `WEB_BIND_ADDRESS` 与 `WEB_PORT` 决定。本仓库本地文件当前是 `127.0.0.1:18080`，模板默认 `127.0.0.1:8080`。登录地址形如 `http://127.0.0.1:18080/login`。容器内 nginx 会把 `/api/` 转到 API，不必再单独起 Vite。

## 本机 API（配合开发模式）

开发模式登录需要本机已有 API。API 用 Bun 启动，依赖 PostgreSQL、Redis，以及 32 字节 `SECRET_ENCRYPTION_KEY`：

```powershell
cd tk-mg-sys\apps\api
bun --cwd . node_modules/drizzle-kit/bin.cjs migrate --config=drizzle.config.ts
bun src/main.ts
```

`DATABASE_URL`、`REDIS_URL`、`SECRET_ENCRYPTION_KEY` 需与 `infra/.env` 一致。默认监听 `3000`。

## 任务 Worker 与系统审计身份

启动顺序：PostgreSQL、Redis → API 迁移 → 确认系统审计用户存在 → API `/ready` 成功 → Worker。API `/health` 仅表明进程存活；`/ready` 还检查 PostgreSQL、Redis 和系统审计用户，缺少该用户时不能视为就绪。Compose 的 worker 等待 API 健康检查；worker 的健康标记只有在启动检查通过后写为 `ready`，停止或故障时健康检查失败。本机独立启动时先完成 API 迁移。生产 worker 使用 `createUnconfiguredDeviceAdapter()`，因此不会连接真实厂商设备；`InMemoryDeviceAdapter` 仅供测试。新的执行任务接口与前端运营中心本地任务列表相互独立。任务级 `parameters` 只能省略或传 `{}`；`input_text` 会被任务 API 拒绝，不能将原文放入任务参数、审计或日志；设备直接命令接口保持原有行为。

`TK_MG_SYSTEM_ACTOR_ID` 必须指向已存在的 `app_user.id`，API 和 worker 必须相同。创建单独、已禁用的系统用户（邮箱和 UUID 按环境替换，密码哈希不要复用登录凭据），不要把管理员或请求人 ID 当作系统身份：

```sql
insert into app_user (id, email, password_hash, role, enabled)
values ('99999999-9999-4999-8999-999999999999', 'task-worker@example.internal', 'not-a-login-hash', 'administrator', false);
```

在本机 API、worker 环境中设置同一个 `DATABASE_URL`、`TK_MG_SYSTEM_ACTOR_ID`；worker 还需唯一 `TK_MG_WORKER_ID`（多个 worker 不可共用）。从仓库根目录运行：

```powershell
pnpm --filter @tk-mg/worker exec bun src/main.ts
```

worker 配置由 Zod 校验；未列出的值使用表内默认值：

| 变量 | 默认 | 范围 |
|------|------|------|
| `TK_MG_WORKER_CONCURRENCY` | 4 | 1–100 |
| `TK_MG_WORKER_POLL_INTERVAL_MS` | 1000 | 50–60000 ms |
| `TK_MG_WORKER_OUTBOX_BATCH_SIZE` | 20 | 1–100 |
| `TK_MG_WORKER_RECOVERY_BATCH_SIZE` | 20 | 1–100 |
| `TK_MG_WORKER_LEASE_MS` | 30000 | 1000–300000 ms |
| `TK_MG_WORKER_HEARTBEAT_MS` | 10000 | 250–60000 ms，必须小于 lease |
| `TK_MG_WORKER_RETRY_DELAY_MS` | 1000 | 0–120000 ms；任务重试的最小间隔，同时仍是 outbox 投递失败的延迟 |

Worker 每周期恢复过期 run/lease，再领取 outbox；outbox claim 默认与 worker lease 同长，投递为至少一次：完成事务后、确认投递前重启可重复收到事件，但已完成任务不会再次提交供应商命令。投递失败最多领取 10 次后进入 `dead_letter`，需人工调查，不能当作已执行成功。任务默认最多 3 次尝试（API 可设置 1–10）；仅确定尚未提交给供应商的失败才按有界指数退避加抖动恢复为 `retry_waiting`，在同一事务将绝对截止时间写入 `next_retry_at` 与重试 outbox 的 `available_at`，到期前其他 worker 不能领取任务或重试事件。尝试次数耗尽写入 `failed` 并清空截止时间。已写 `submit_started_at` 的步骤不能因 failed、timed_out 或 not_found 自动重提，结果不明时隔离设备等待复核。有序步骤只在前一步成功后领取；不确定的适配器提交结果须用原 command ID/幂等键恢复，不能推断为成功。停止进程会中止活动执行且不确认未完成的 outbox，过期后由其他 worker 恢复。适配器调用超时只限制本进程等待时间，不证明远端停止或取消；不能保证供应商物理执行恰好一次。

任务终态的数据库投影只保留归一化信息：供应商确认的成功使用最后一个成功步骤的安全结果；失败、超时和取消保留归一化错误；管理员人工确认成功只记录 `operator_verified` 证据，任务及待确认步骤的结果仍为空。任务详情和列表不会返回任务或步骤的结果与错误字段。API 自身不能查询供应商结果，过期且已提交但结果不明的 run 会进入 `needs_reconciliation`，设备租约保持隔离，不能凭租约超时重新提交。组内管理员可用 `POST /api/groups/:groupId/tasks/:taskId/reconcile` 提交终态决议及不含凭据的 `evidenceRef`；应先独立核实供应商结果，重复相同决议是幂等的，不应伪造供应商结果。

## 本地验证

日常提交前从仓库根目录运行：

```powershell
corepack pnpm typecheck
corepack pnpm lint
corepack pnpm test
corepack pnpm build:web
```

`pnpm test` 包含 Web Vitest、API/Worker Bun 单测及共享包测试。PostgreSQL 集成测试默认跳过；运行真实数据库前须创建单独的 `tk_mg_test_*` 库，脚本会重建它的 `public` schema（不要并发运行使用同一数据库的套件）：

```powershell
$env:TEST_DATABASE_URL = "postgres://tk_mg:密码@127.0.0.1:5432/tk_mg_test_p4"
pnpm --filter @tk-mg/api test:postgres
pnpm --filter @tk-mg/worker test:integration
pnpm --filter @tk-mg/worker test
pnpm typecheck
pnpm lint
pnpm test
pnpm --filter @tk-mg/web build
Remove-Item Env:TEST_DATABASE_URL
```

可用现有 `pnpm test:postgres:local` 创建本机 Docker disposable PostgreSQL 并运行 API 套件；随后将 URL 指向脚本创建的 `tk_mg_test_local` 库运行 worker integration。`TEST_DATABASE_URL` 必须以 `tk_mg_test_` 为库名前缀；API 套件重新迁移会清空该测试库的数据，worker integration 依赖前一步已经迁移。未配置 URL 时 `pnpm test` 中数据库用例显示 skip，不能视为 PostgreSQL 通过；显式 integration 命令无 URL 会退出非零。旧设备命令路由和适配器契约继续随全量 `pnpm test` 运行，真实库命令用例随 API `test:postgres` 运行。

最小浏览器冒烟使用 Playwright Chromium，并通过路由拦截模拟认证 API：

```powershell
corepack pnpm --filter @tk-mg/web exec playwright install chromium
corepack pnpm test:e2e:smoke
```

Web 单测在 `apps/web/vite.config.ts` 中将 Vitest 文件级并行限制为 2 个 worker，避免 Ant Design/jsdom 重型用例在本机或 CI 中互相抢占导致超时。完整 Web 单测耗时约 6 分钟，属于当前基线。
