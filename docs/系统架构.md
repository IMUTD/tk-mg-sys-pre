# 系统架构

整个系统由三套程序组成：init-tool、sys 和 RPA-agent。三者都读写同一个 PostgreSQL 库 `tk_mg`。sys 不连盒子的局域网地址，打盒子接口的只有 init-tool 和 agent。各程序内部的交互细节见 `docs/三端逻辑.md`。

```text
                        浏览器（管理员 / 成员）
                                │ HTTPS
                     ┌──────────▼───────────┐
                     │ web：nginx + React   │
                     │  /api/*、/agent/* ───┼─────┐
                     └──────────────────────┘     │
                                                  ▼
 支付宝 ◄── 下单、查询、退款 ──  ┌───────────────────────────────┐
 支付宝 ── 付款回调 ──────────►  │ api（Bun + Hono，端口 3000）   │
                                │  登录、成员权限、盒子、账号      │
                                │  行为链、任务、调度、分享文件     │
                                │  agent 协议、画面中转            │
                                │  盒子时长：订单、退款、到期限制   │
                                └──────┬──────────────┬─────────┘
                                       │              │ 只在启动和健康检查时 ping
                                       ▼              ▼
     ┌───────────────┐   ┌──────────────────────┐   Redis
     │ worker        │──►│ PostgreSQL：tk_mg     │
     │ 通用任务执行器 │   │ 账号、盒子、任务、订单 │
     └───────────────┘   │ 审计、box_fee …       │
                         └────▲────────────▲─────┘
                              │            │
              管理员、盒子、分配、费用        注册、心跳、领任务、回报、画面
                              │            │（Bearer 令牌，经 /agent/*）
                 ┌────────────┴──┐     ┌───┴──────────────────┐
                 │ init-tool（Go）│     │ RPA-agent            │
                 │ 127.0.0.1:18789│     │ 一台盒子一个          │
                 └──────┬────────┘     └───┬──────────────────┘
                        │ UDP 7678 扫描、:8000 │ 盒子 RPA / 安卓接口
                        ▼ 镜像、云机           ▼ 执行技能、截图
                     ┌───────────────────────────────┐
                     │        局域网里的盒子            │
                     └───────────────────────────────┘
```

## 1. 组件

| 组件 | 位置 | 职责 |
| --- | --- | --- |
| web | `apps/web` | React 和 antd 写的管理后台，由 nginx 托管。nginx 把 `/api/`、`/agent/` 转给 api |
| api | `apps/api` | 核心服务，几乎所有业务都在这里，见第 2 节 |
| worker | `apps/worker` | 执行 `executor_key = device-command` 的通用任务，通过 outbox 处理状态变化。设备适配器还是未配置的空实现，盒子任务不经过它 |
| PostgreSQL | `infra/postgres` | 唯一的业务库。表结构由 drizzle 迁移维护，见 `apps/api/src/db/migrations` |
| Redis | — | api 启动时连接，只在健康检查里 ping，没有业务在用 |
| init-tool | 仓库 `hmg-init-tool`（Go） | 跑在客户机上，不需要登录。扫描盒子，管镜像和云机，建管理员，分配盒子，录入 `box_fee` 费用 |
| RPA-agent | 不在这两个仓库里 | 一台盒子一个进程。向 sys 注册并心跳，长轮询领任务，一次只做一步，回报结果，有人观看时推送画面 |

## 2. api 内部的模块

代码在 `apps/api/src/modules`。

| 领域 | 主要代码 | 内容 |
| --- | --- | --- |
| 登录和权限 | `auth`、`members`、`access`、`audit` | cookie 会话 `tk_mg_session`、成员和上下级 `parent_user_id`、页面权限、审计日志 |
| 盒子 | `box-link.ts`、`devices` | 盒子列表、备注和分组、坑位、画面，以及 agent 协议 `/agent/*` |
| 行为和任务 | `box-link.ts`、`guards.ts`、`task-execution` | 行为链、`POST /api/tasks` 下发、按步骤领取、守护 |
| 运营调度 | `dispatch`、`account-pool`、`proxies` | 批量把账号分到盒子和坑位上执行 |
| 分享文件 | `share-files.ts` | 扫描盒子的共享目录，在盒子之间转移文件 |
| 盒子时长和支付 | `box-service.ts`、`box-service-limit.ts` | 支付宝下单、回调、查询、退款，到期限制，读取费用记录，见第 4 节 |
| init-tool 同步 | `initializer-sync`、`src/init-sync.ts` | 手动运行的脚本，把 init-tool 旧版 `init_*` 表的数据同步进 `tk_mg` |

## 3. 账号和可见范围

| 账号 | 来源 | 识别方式 |
| --- | --- | --- |
| 平台方 | 部署时 `initialize` 容器创建 | `role = administrator` 且 `provisioned_by = sys` |
| 管理员 | init-tool 创建 | `role = administrator` 且 `provisioned_by = init-tool` |
| 成员 | 在 sys 成员管理里创建 | `parent_user_id` 记录创建人 |

盒子靠 `device.assignee_user_id` 归属到管理员。同一个 `user_group` 的人看到同一批盒子。平台方能看到全部盒子，包括还没分配的。

## 4. 盒子时长和支付

支付不是独立服务，而是 api 里的一个模块：和主系统共用进程、数据库、登录会话、页面权限和审计。

### 4.1 购买流程

1. 「盒子时长」页面调用 `POST /api/box-service/orders`，后端写入一条 `box_service_order`，状态 `pending`，再返回支付宝收银台地址（`alipay.trade.page.pay`，30 分钟内付款有效）。
2. 支付宝回调 `/api/pay/alipay/notify`。后端验签，并核对订单号、金额和应用 ID。用户也可以在订单页点「查询支付结果」，后端改用 `alipay.trade.query` 去查。待支付和已关闭的订单都有这个按钮。
3. 确认付款后，在同一个事务里把订单改成 `paid`，并延长 `device.service_until`：没到期就从原到期时间往后加，已到期就从现在开始算。同一笔订单只加一次时长。付款时盒子已经被删掉的，订单照样记为已支付，订单页标出「盒子不存在」，并写审计 `box_service.order.device_missing`，留给人工处理或退款。
4. api 每 5 分钟补查一次下单超过 35 分钟、还在待支付的订单，防止回调丢失：
   - 支付宝说已付款，就当场到账；
   - 支付宝说交易已关闭，就关闭订单；
   - 下单超过 2 小时，且支付宝说没有这笔交易或还没付，就关闭订单；
   - 查不到结果（超时、网关不通）就等下一轮，超过 1 天仍查不到才关闭。
   已关闭的订单如果后来收到付款回调或手动查到已付款，照样到账。

调用支付宝的请求都有 10 秒超时。

### 4.2 退款

只有平台方能退款，只能整单退已支付的订单，必须填写原因。接口是 `POST /api/box-service/orders/:outTradeNo/refund`，调用的是 `alipay.trade.refund`。

- 退款请求号固定为 `订单号-refund`，重复点不会重复退钱。
- 退款成功后，订单改为 `refunded`，并从 `service_until` 扣掉这笔订单的月数。
- 支付宝拒绝时，订单保持 `paid`，时长不变，页面显示支付宝返回的原因。
- 成功和失败都写审计 `box_service.order.refund`。

### 4.3 到期限制

受限的盒子没有 `service_until`，或者已经到期，就不能接新任务，接口返回 `service_expired`。这四个入口都会拦：

| 入口 | 接口 | 到期时的表现 |
| --- | --- | --- |
| 手动下发 | `POST /api/tasks` | 403 |
| 分享扫描 | `POST /api/share-scans` | 跳过这台盒子，状态记为 `expired` |
| 分享转移 | `POST /api/share-transfers` | 源盒子或目标盒子已到期时返回 403 |
| 开始调度 | `POST /api/groups/:groupId/dispatches/start` | 409，列出已到期的盒子，整批不开始 |

到期前已经排队的任务照常执行。查看、备注、分组这些功能不受影响。

哪些盒子受限，由环境变量 `BOX_SERVICE_LIMITED_HOSTS` 决定，按盒子当前 IP 匹配：

| 值 | 效果 |
| --- | --- |
| 不设 | 只限制 `192.168.76.166`（测试阶段） |
| `ip1,ip2` | 只限制列出的 IP |
| `*` | 限制全部盒子 |

### 4.4 费用记录

init-tool 往 `box_fee` 表录费用，sys 在「时长订单」页的「费用记录」标签下只读展示。费用按 `box_fee.box_id = device.external_id` 对应到盒子，归到盒子当前的管理员名下。库里没有这张表时，页面显示「还没有费用记录表」。

### 4.5 谁能看到什么

| 账号 | 能买的盒子 | 能看的订单 | 能看的费用 |
| --- | --- | --- | --- |
| 平台方 | 全部，包括还没分配的 | 全部 | 全部，并显示所属管理员 |
| 管理员和成员 | 分给自己、下级或同组的盒子 | 自己和下级下的单 | 当前分给自己或下级的盒子的费用 |

### 4.6 配置

| 变量 | 作用 |
| --- | --- |
| `ALIPAY_APP_ID`、`ALIPAY_PRIVATE_KEY`、`ALIPAY_PUBLIC_KEY` | 支付宝应用、应用私钥、支付宝公钥。三个都配了才会开放下单 |
| `ALIPAY_GATEWAY` | 默认是正式网关，测试时换成沙箱网关 |
| `ALIPAY_NOTIFY_URL`、`ALIPAY_RETURN_URL` | 归积分商城使用（`/api/pay/alipay/mall/notify`），盒子时长不读这两个 |
| `BOX_SERVICE_ALIPAY_NOTIFY_URL` | 盒子时长的支付宝回调地址，`https://<域名>/api/pay/alipay/notify`。可不填：不填时取 `ALIPAY_NOTIFY_URL` 的域名拼上这个路径；两个都没填就只能靠补查到账 |
| `BOX_SERVICE_ALIPAY_RETURN_URL` | 盒子时长付款后跳回的页面，`https://<域名>/operations/box-service`。可不填：不填就跳回下单时所在域名的这个页面 |
| `BOX_SERVICE_PRICE_1/3/6/12` | 各档套餐价格，默认 100、270、500、900 元 |
| `BOX_SERVICE_LIMITED_HOSTS` | 到期限制的范围，见 4.3 |

`infra/docker-compose.yml` 和 `infra/compose.prod.yml` 都会把这些变量传给 api。代码还会读取 `/workspace/alipay.local.env` 作为补充，只填环境里没设的变量。

相关迁移：`0082_box_service`（订单表和 `service_until`）、`0083_app_user_parent`（上下级）、`0084_box_service_refund`（退款状态和字段）、`0085_box_service_device_missing`（付款时盒子是否已删除）。

## 5. 主要数据流

1. **开通盒子**：init-tool 扫到盒子并建好管理员，把盒子分配出去，写入 `app_user` 和 `device`，管理员就能登录 sys 看到自己的盒子。
2. **下发任务**：页面写入 `execution_task` 和每一步的 `execution_task_step`，再用 `pg_notify` 唤醒 agent。agent 每次领一步，执行完回报，然后领下一步。
3. **看画面**：页面写入 `device_watch` 登记观看，agent 从心跳回应里得知后开始推截图。sys 只在内存里中转，页面用 `GET /api/frames` 拉取。
4. **购买时长**：见第 4 节。

## 6. 部署

生产用 `infra/compose.prod.yml`，包含 postgres、redis、api、worker、web 五个容器。首次部署时，一个一次性的 `initialize` 容器（profile `bootstrap`）先跑数据库迁移，再创建平台方管理员。init-tool 和 agent 不在这份部署里，分别跑在客户机和盒子旁边。

## 7. 已知的出入和缺口

- **init-tool 写入哪个库**：`docs/三端逻辑.md` 说 init-tool 只写自己的 `hmgdb`，但 init-tool 的 `feat/scan-lock-and-quota` 分支已经改成直接写 `tk_mg` 的 `app_user` 和 `device`。实际以哪种方式运行，要看部署时 `INIT_DATABASE_URL` 指向哪个库。
- **配额拦截**：init-tool 分配盒子时还会检查配额（`internal/store/pg.go`），和「不再有配额」的决定冲突。
- **到期限制按 IP 匹配**：盒子换了 IP，限制不会跟着走。
- **退款没有实测**：还没在支付宝沙箱里实际跑过。
- **Redis 和 worker**：Redis 没有业务在用，worker 对盒子业务也不起作用。
